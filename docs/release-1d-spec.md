# Release 1D：Violet Continuity 最终规格

> 状态：方案已批准；Phase 1 第三轮审查修复已提交、复审、合入双主线并重新部署；
> Phase 2/3 未开始。本文是 Release 1D 的产品与技术事实源。
> 实施顺序见 [任务拆分](./release-1d-tasks.md)，放行条件见
> [验收清单](./release-1d-acceptance.md)。

## 1. 目标

Release 1D 让 Violet 在文字、语音、Core 重启和跨天使用中保持连续：能正确使用用户
过去明确表达的信息，所有记忆都有来源，用户可以查看、纠正和删除，删除内容不会经
Violet 官方恢复流程复活。

成功体验是：

1. 用户用语音表达长期偏好；
2. 重启 Mac App 和 Core；
3. 用户切到文字，Violet 无需重复说明即可正确使用；
4. 用户纠正后，下一次语音只使用新版本；
5. 用户能查看来源并删除；
6. 删除前备份被官方恢复流程拒绝，删除后备份恢复不出旧内容。

## 2. 范围

### 2.1 本次交付

- PostgreSQL 加密事件账本继续作为唯一原始事实源。
- 原子长期记忆：内容、来源、时间、类型、版本、敏感级别和状态。
- 不超过 8,900 UTF-8 bytes 的有界 `memory_summary`。
- 每个内部上下文 epoch 最多一个滚动 `ContextCheckpoint`。
- 文字与语音共用的 `ContextAssembler`。
- 一个内部 `recall_memory(query, from?, to?)` 工具。
- Mac 独立记忆窗口：当前记忆、近期变化、来源、纠正、删除和自动记忆开关。
- 删除传播和 Violet 官方恢复防复活。
- 自动提取、检索、纠正、删除和性能评估集。

### 2.2 明确不做

- 不新增服务、第二 Agent 运行时或独立消息队列。
- 不做主题记忆、每日摘要、每日文件或文件系统事实源。
- 不做向量检索、embedding、RRF 或模型重排。
- 不做数值置信门槛、低置信待确认队列或第二语义裁判。
- 不从助手回复、工具结果、视觉结果、临时语音或取消语音中提取用户事实。
- 不自动回填 1D 上线前历史；旧历史只在用户明确回忆时搜索。
- 不做逐记录密钥注册表或密码学级逐记录销毁。

若固定验收集证明文本检索达不到召回门槛，再单独设计向量检索；本次不预埋双链路。

### 2.3 已确认的七个边界

| 边界 | 1D 处理 |
|---|---|
| 内部上下文 | 不可见 epoch；Core 重启或 30 分钟空闲后结束 |
| ASR 错误 | 最终转写允许被提取；近期变化中可见、可追源、易删除 |
| 敏感记忆 | 明确要求时按原话保存，不再发给提取模型 |
| 删除来源轮次 | 模型理解目标，Core 查真实 ID，确认页展示全部影响 |
| 陈旧 summary | 绑定 memory revision，不匹配就停用 |
| 检索不足 | 先跑固定验收集，未达标才设计向量检索 |
| 批量治理 | 关闭只停新增；清空独立确认 |

## 3. 总体结构

```text
文字 / 语音
    ↓
Core
├── ContextAssembler
│   ├── memory_summary
│   ├── 当前 epoch 的一个 checkpoint
│   └── 最近完整轮次
├── recall_memory
├── 记忆提取与治理
└── 删除传播
    ↓
PostgreSQL
├── conversation_events（唯一原始事实）
├── memories + sources
├── memory_summary
├── context_checkpoint
└── deletion tombstones
```

- 领域合同留在 `packages/domain`。
- PostgreSQL、模型和备份实现在现有服务内，不拆新服务。
- Mac 只通过版本化 Core API 管理记忆，不直连数据库。
- summary、checkpoint 和搜索结果都是不可信数据，不能覆盖系统、安全或授权规则。

## 4. 连续上下文

### 4.1 内部 epoch

- `context_epoch` 不对用户显示。
- Core 重启后结束当前 epoch。
- 同一 Core 连续 30 分钟没有有效最终用户输入后结束当前 epoch。
- 文字和语音共享 epoch，切换输入方式不会结束。
- 新 epoch 不直接注入旧 epoch 的近期原文和 checkpoint；仍可使用长期记忆或按需检索。

### 4.2 ContextAssembler

文字、Pipeline 语音和 Qwen 语音必须使用同一个装配入口，顺序为：

1. 系统与安全指令；
2. 版本匹配的 `memory_summary`；
3. 当前 epoch 的 checkpoint；
4. checkpoint 之后的完整轮次；
5. 当前用户输入和当前轮已授权的临时 Context；
6. `recall_memory` 工具定义。

预算规则：

- 每个模型 adapter 声明 context window。
- 供应商只声明轮次或时长限制而不声明 token window 时，adapter 还必须声明 Violet
  自己执行的保守文本预算，不能借用 checkpoint 模型的预算。
- 优先预留供应商声明的最大输出；缺失时预留 16,384 tokens。
- 再预留 4,096 tokens 安全余量。
- 压缩后尽量保留最近 20,000 tokens 的完整轮次。
- Qwen 保留 `max_history_turns = 20`。
- Qwen 当前额外使用 Violet 侧 131,072-token context envelope、16,384-token 输出预留
  和相同的保守 UTF-8 估算；这是产品安全上界，不冒充供应商只按
  [轮次和音频时长](https://help.aliyun.com/zh/model-studio/qwen-audio-realtime-user-guides)
  公布的容量规格。

超限只允许：

1. 大型工具或视觉文本在入口截断，并保留来源 ID、原长度和 hash；
2. 把最旧完整前缀与已有 checkpoint 压成一个新 checkpoint；
3. 仍超限时扩大被压缩前缀并重试一次；
4. 再失败则明确返回上下文压缩失败，不静默截断半轮。

checkpoint 由当前配置的文字模型生成，不新增模型、供应商或第二套摘要运行时。Core 只在
来源范围和 deletion revision 仍匹配时加密保存。

checkpoint 水位必须是连续的完整逻辑轮次前缀：任何更早但尚未完成的 request 都会阻止
水位越过它；读取已有 checkpoint 和事务保存时都要重新验证。关闭
`VIOLET_CONTEXT_CHECKPOINT_ENABLED` 后不得读取或写入已有 checkpoint，只能使用有界
完整轮次。

文字请求在用户事件落账后失败或取消时，Core 写入不含正文的终止标记。终止轮次不进入
模型历史，但不再永久阻塞后续完整前缀；相同 `request_id` 重试时先清除标记。并发文字
请求的 epoch 分配按输入到达顺序串行化，时间水位只能单调前进。

Integrated Realtime 会话除了绑定 epoch，也绑定建立连接时的账本水位。同一 epoch
若被文字入口或其他连接写入新轮次，下一次输入在到达持有旧历史的供应商前必须失败并
关闭，重连后重新装配。Pipeline 每轮必须先持久化最终用户输入，并以该事件 sequence
作为装配上界。Integrated Realtime 的自动 VAD 轮次在最终转写前缓存供应商回答，复核
账本快照后才可对客户端可见。视觉工具调用产生的中间取消不结束逻辑轮次，最终 grounded
回答仍须与用户输入使用同一 epoch 落账。

## 5. 长期记忆

### 5.1 数据

只增加满足当前需求的持久状态：

- `context_epochs`：不可见的当前对话边界；
- `memories`：一条可独立理解的原子主张及其版本、类型、敏感级别和状态；
- `memory_sources`：记忆到最终用户事件及原文位置的关系；
- `memory_summary`：有界派生视图及其 `memory_revision`；
- `context_checkpoints`：当前 epoch 的滚动 checkpoint；
- `memory_jobs`：不含正文的异步提取任务；
- `deletion_tombstones`：不含正文和语义的最小删除记录。

所有语义正文使用现有 `EnvelopeCipher` 加密。来源引用不重复保存原文，只保存用户事件 ID
和 UTF-8 byte offset；Core 解密原事件后必须逐字验证。

1D 用“用户原话来源是否有效”表达记忆可信度，不保存或使用模型自报的数值置信分。
1D 的记忆影响范围固定为 Violet 自身对话中的理解与回答；记忆本身不授予工具、外部
发送、现实行动或新的数据访问权限。

`memory_summary` 只由当前记忆确定性拼接，不调用额外模型。明确记忆优先，其余按最近
更新时间排序；达到 8,900 bytes 后停止加入完整条目。summary revision 与当前记忆
revision 不一致时完全停用。

### 5.2 写入

- 用户明确“记住”或纠正时同步处理，本轮完成前确定成功或失败。
- 普通完成轮次异步提取，不阻塞回复。
- 当前配置的文字模型负责判断长期价值、拆成原子主张和识别重复/冲突，不新增模型。
- Core 只校验 Schema、最终用户来源存在、原文引用匹配、秘密、版本和幂等。
- 自动提取可以新增记忆或给现有记忆增加来源，不能自动取代旧版本。
- 只有用户明确纠正可以创建新版本并让旧版本立即失效。
- 矛盾但都有来源的内容可以并存；使用时表达变化或不确定性。
- 延迟结果写入前必须再次检查来源仍存在且没有删除墓碑。

模型提议不能把助手、工具或视觉内容当成用户事实。只有完整助手回复后的最终轮次进入
自动提取；部分语音、取消回复和孤立助手消息不进入。

### 5.3 敏感信息

- 密码、验证码、Token、私钥等绝对秘密永不写入记忆或派生内容。
- 普通受控敏感内容不自动记忆。
- 用户明确要求记住受控敏感内容时，按用户原话加密保存，不再额外发送给提取模型。
- 受控敏感记忆召回时仍遵守正常模型隐私规则。

### 5.4 自动记忆开关

- 默认开启。
- 关闭只停止新增，不删除已有记忆。
- 关闭期间的轮次在重开后不补提取。
- “清空已学习记忆”是独立危险操作，必须单独确认。

## 6. 检索

`recall_memory` 是 1D 唯一新增的记忆工具：

- 参数是 query 和可选 ISO 8601 `from`、`to`；
- 最多返回 5 条；
- 返回内容、发生时间、更新时间、来源事件和当前/历史状态；
- 先做 Unicode NFKC、大小写与空白规范化，再按文本命中和时间筛选；
- 搜索在 Core 内存中解密完成，不建立明文数据库索引；
- 明确询问“之前、上次、昨天、原话”等时，也可搜索未删除的旧事件账本；
- 没有结果时返回 `not_found`，Violet 必须说想不起来。

当前摘要足够时不调用；过去时间指代、核对原话、纠正/删除消歧或摘要不足时调用。文字
和语音使用同一实现。

## 7. 查看、纠正与删除

### 7.1 Mac 记忆窗口

菜单栏浮窗提供一个记忆图标，打开独立窗口。窗口包含：

- 当前记忆与近期变化；
- 搜索、类型筛选和时间排序；
- 内容、版本、明确/自动来源、时间和来源轮次；
- 纠正、删除和自动记忆开关；
- 独立的“清空已学习记忆”入口。

写入反馈只表现为记忆入口的变化标记，不弹 toast，不增加额外聊天气泡。受控敏感正文
在列表中默认遮挡，用户进入详情后主动显示。

### 7.2 纠正

- 纠正追加新版本，不改写旧原文。
- 新版本写入与旧版本失效在同一事务完成。
- 删除纠正来源后，旧版本也不自动复活。

### 7.3 删除

- 用户自然表达“忘掉”时，模型理解目标并生成删除预览，不直接执行。
- 模型只理解并提议删除目标，Core 解析真实 ID，不能由模型直接执行。
- 删除前展示完整影响范围：用户输入、对应助手回复、受影响记忆及仍有其他来源的记忆。
- 用户确认后，删除整个逻辑来源轮次，不做原文局部改写。
- 同一 `request_id` 的用户输入、助手回复及相关派生物一起删除。
- 删除一条记忆时，删除支撑它的全部来源轮次；用户也可以只删除其中一个来源。
- 清空已学习记忆时，删除支撑现有记忆的全部来源轮次。
- 多来源记忆删除一个来源后可以保留；最后一个来源消失时删除记忆。
- 在线删除立即使 memory、summary、checkpoint、搜索和迟到任务停止使用目标内容。
- 审计只保留删除 ID、时间、设备、作用域、状态和策略版本，不保留正文或语义。

## 8. 官方恢复不复活

- 每次确认删除都增加 PostgreSQL 中的 `restore_epoch`。
- Mac Keychain 保存 `minimum_restore_epoch`，只允许增加。
- 备份格式记录并认证自身 `restore_epoch`。
- Violet 官方恢复脚本在恢复前读取 Keychain，拒绝低于最低纪元的备份。
- 删除后生成并验证一份干净备份，再清理 Violet 管理的删除前远端版本和本地副本。
- 清理失败不撤销在线删除；旧备份仍因 Keychain 纪元被官方恢复流程拒绝。
- 新备份恢复后，事件、记忆、summary、checkpoint 和检索中都不能出现已删除内容。

这满足“Violet 恢复流程不可复活”。用户自行绕过 Violet、复制并手工读取数据库文件，
不在 1D 的承诺范围内。

## 9. API 与事件

在现有 `/v1` 协议中增加最小管理面：

- 列出记忆和读取单条来源；
- 提交纠正；
- 读取/修改自动记忆开关；
- 生成删除预览、确认删除、查询备份清理状态。

所有写操作必须幂等；纠正和删除预览使用版本检查，状态已变化时要求刷新。文字
`complete` 和语音 `response.completed` 可以携带不含正文的 `memoryChanges`，Mac
只用它更新记忆入口。

## 10. 验收门槛

- 明确记住成功率 100%。
- 自动记忆精确率不低于 95%，召回率不低于 80%。
- 明确历史 Top-5 召回率不低于 90%。
- 绝对秘密写入、助手推断冒充用户事实、纠正或删除后继续使用旧内容均为 0。
- 健康环境异步提取 p95 不超过 60 秒。
- 本地检索 p95 不超过 300 ms。
- 模型、并发、时序和性能测试保留全部试验与分布。
- 每次自动化和真人验收都有独立 `.local-acceptance/test-runs/` 记录。

## 11. 依赖、发布与回滚

- 复用现有 PostgreSQL、DeepSeek `deepseek-flash`（DeepSeek-V4.1-Flash）、Qwen、
  TOS、Mac Keychain、OpenAPI 和测试记录器。
- 不新增 npm/Swift 依赖、外部账号或凭证；现有 `pgvector` 扩展不参与 1D 检索。
- Swift 实现和验收前需由用户接受本机 Xcode license；规格本身不受影响。
- 发布顺序是：统一上下文 → 明确记忆与治理 → 自动提取。
- 自动提取验收完成前保持关闭；通过后才设为默认开启。
- 可分别关闭自动提取、记忆注入和 checkpoint；已写记忆仍可查看、纠正和删除。
- 回滚不得降低 `restore_epoch`、恢复旧版本或重新关联已删除来源。

## 12. 与基线文档的关系

本规格把路线图中的六类完整记忆、混合向量检索和逐记录密钥销毁从 1D 必做项移出，
但不否定它们作为有证据后的长期候选。相关表述已同步到
[工程路线图](./engineering-roadmap.md)和[总体架构方向](./architecture-direction.md)。
