# Release 1B 实时语音验收

> 状态：已完成。Qwen 为默认运行时，Pipeline 为显式配置的手动降级与供应商替换基线。

本文定义 Qwen 端到端候选的可重复设备验收方法。自动化测试不得占用真实麦克风、播放声音、锁屏或睡眠；以下真实设备步骤只在用户明确批准的验收窗口执行。

## 1. 记录边界

验收记录默认关闭。启动脚本只为本次 App 进程设置 `VIOLET_ACCEPTANCE_LOG`，Mac App 随后向指定本地 NDJSON 文件追加事件。

记录内容仅限：

- 单调时钟毫秒数和 ISO-8601 时间。
- 事件类型、停止或触发原因。
- 随机生成的 run、session、turn、response 和 trigger ID。

禁止写入音频字节、转写、回复文字、设备令牌、供应商密钥、模型内部推理或用户文件内容。汇总器遇到未列入 schema 的字段会直接拒绝报告。

## 2. 启动验收构建

先确认 Kerberos 票据有效；失效时由用户在自己的终端执行交互式 `kinit`：

    klist -s || kinit

批量调用真实 Qwen 前同时确认本轮累计费用不会超过已批准的 ¥20 试跑上限。

    pnpm macos:app

先退出正在运行的 Violet，再启动带本地记录的同一构建：

    ./scripts/start-macos-acceptance.sh

默认日志位于 .local-acceptance/，该目录不进入 Git。也可以传入一个明确的输出路径：

    ./scripts/start-macos-acceptance.sh /absolute/path/realtime.ndjson

## 3. 定量验收矩阵

同一份正式报告至少包含：

| 门禁 | 样本 | 通过标准 |
|---|---:|---|
| 浮层触发 | 100 | 从点击或快捷键到 popoverDidShow 的 p95 不超过 200ms |
| 真实语音 | 30 | 从服务端判定停止说话到首个本地音频分片排队的 p95 不超过 2s |
| 回复打断 | 30 | 从本地或服务端检测到打断到调用停播的 p95 不超过 300ms |
| 麦克风停止 | 50 | 从停止请求到采集关闭的 p95 不超过 1s |
| 已取消回复 | 全部 | 停播后旧 response 再次排队播放的次数为 0 |
| 会话失败 | 正常样本 | 非预期失败次数为 0 |

建议样本组成：

- 30 次语音：10 次中文、5 次英文、5 次中英混合、5 次长停顿、5 次日常背景噪声。
- 30 次打断：20 次直接说话、10 次点击；耳机和扬声器各覆盖至少 10 次。
- 50 次停止：20 次收起浮层、10 次主动停止、10 次锁屏、5 次睡眠/唤醒、5 次连接超时或断线。
- 100 次触发：菜单栏点击与 Control + Option + Space 各 50 次，并覆盖常见前台应用。

该语音延迟是服务端断句后的内部指标，不包含用户停声到服务端 VAD 判定的时间。完整端到端延迟、系统静音、勿扰、耳机切换和扬声器回声需要在样本备注中人工判定；日志只证明状态机调用时序，不能代替“实际开始播放”和“实际没有继续出声”的听觉确认。

## 4. 生成报告

退出本次 Violet 后执行：

    pnpm acceptance:report -- .local-acceptance/<file>.ndjson

命令输出每项的样本数、p50、p95、最差值、迟到播放次数和失败会话数。全部门禁满足时退出码为 0；样本不足或任何门禁失败时退出码为 1；文件或 schema 非法时退出码为 2。

## 5. 故障与恢复验收

故障注入使用独立日志，不与正常定量样本混合：

1. 断开并恢复 SSH 隧道，确认 UI 明确离线并在隧道恢复后重新变为 Ready。
2. 在监听、处理和播放三个状态分别断网，确认麦克风与播放停止，且不会静默切换供应商。
3. 让实时连接正常关闭、异常关闭和超时，确认可以重新开启新会话。
4. 在旧响应取消后注入迟到文字和音频事件，确认它们不会覆盖新回复或重新播放。
5. 切换耳机、内置扬声器和麦克风路由，确认系统音量不被压低，并记录回声误触发情况。

故障恢复证据包括 UI 状态、Core 健康状态和验收事件报告。原始音频和消息内容不作为证据保存。

## 6. 2026-08-23 Qwen 候选结果

候选提交 `462d894` 的正常样本已经通过四项定量门禁：

| 门禁 | 样本 | p50 | p95 | 最差 | 结果 |
|---|---:|---:|---:|---:|---|
| 浮层触发 | 174 | 14ms | 18ms | 141ms | 通过 |
| 服务端断句到首个音频分片 | 88 | 110ms | 501ms | 991ms | 通过 |
| 回复打断 | 31 | 1ms | 4ms | 5ms | 通过 |
| 麦克风停止 | 54 | 7ms | 15ms | 23ms | 通过 |

触发样本包含 50 次菜单栏点击和 124 次快捷键；前 30 个正式打断样本由 20 次直接语音和 10 次点击组成。全部正常样本的配对成功率为 100%，已停止回复重新排队播放为 0，正常会话失败为 0。

原始本地日志保留故障注入事件。正式 normal 视图只排除了三个明确的故障会话和一个在采集开始前即关闭的会话，不修改其余事件内容：

- 供应商空闲连接在约 180 秒后关闭，麦克风随即停止；同一 App 可重新建立会话。
- 在监听态和播放态分别中断 SSH 隧道，活动会话均停止采集；隧道约 3 秒后自动重建，新会话可再次进入 Listening。
- 使用单向 250ms 的本地 TCP 延迟代理时，健康请求约 528ms，Realtime 会话仍可建立并完成语音回复；恢复直连后健康请求约 89ms。
- 外置麦克风/耳机、Bluetooth 和 MacBook 内置麦克风/扬声器均可建立真实采集会话；内置路由还完成了输入、回复播放和打断。

本轮没有重复执行 10 次真实锁屏和 5 次整机睡眠，因为这些操作需要用户解锁并会中断当前桌面工作。此前真实锁屏、显示器睡眠和 46 秒 Deep Idle 恢复均已通过；发布前仍需由用户在场完成建议次数的最终抽样。

## 7. 2026-08-24 Pipeline 初始基线

提交 `3e0e2ab` 使用同一 `RealtimeConversationPort` 接入 `paraformer-realtime-v2 → deepseek-v4-flash → cosyvoice-v3-flash`。实时路径关闭 DeepSeek thinking，普通文字聊天保持原配置。

为避免在办公环境外放，canary 全程在 Devbox 内存中完成：CosyVoice 生成的 24kHz PCM 不落盘、不播放，内存降采样到 16kHz 后直接送入 Paraformer。三次测试均准确转写“你好，这是静默语音测试。”：

| 样本 | 文本输入到首音频 | Paraformer 断句到首音频 |
|---|---:|---:|
| 1 | 1.10s | 1.94s |
| 2 | 1.24s | 1.92s |
| 3 | 1.22s | 1.34s |

另一次长回复取消 canary 在首个音频分片后取消模型与 CosyVoice 任务，随后 1 秒内迟到音频为 0，且未产生取消后的完成事件。

该结果证明 Pipeline 基线可运行并满足三次初始样本的 2 秒内部延迟门禁。Qwen 当前 88 次样本的 p95 为 501ms，且已通过更完整的设备、弱网和恢复矩阵，因此确定为 Release 1B 默认运行时；Pipeline 保留为显式配置的手动降级与供应商替换基线，不做静默自动切换。完整同集比较只在准备更换默认运行时，或 Qwen 的质量、费用、地域和稳定性证据恶化时恢复。

## 8. 账本与隐私收尾

在临时 PostgreSQL 数据库中执行了真实 `Pipeline → RealtimeSession → PostgresConversationLedger` 闭环：

- 最终用户转写和助手回复生成并恢复为两条 `user`、`assistant` 事件。
- 内容字段使用 AES-256-GCM 信封加密，数据库只保存密文、nonce、tag 和 wrapped key。
- `conversation_events` 不包含 audio、transcript 或 reasoning 原文字段。
- 原始 PCM 只存在于进程内存，未写入日志或磁盘。
- 验证完成后临时数据库已删除，正式账本未写入测试事件。
- 最终部署恢复既有 Devbox 数据目录并确认 411 条加密事件完整。

结合此前真实锁屏、显示器睡眠和 Deep Idle 证据，Release 1B 的当前交付范围验收完成。重复锁屏、整机睡眠和更大规模的 Pipeline 同集比较保留为后续回归，不阻塞 1C。
